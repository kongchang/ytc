# คู่มือทำให้ระบบปลอดภัยขึ้น (อ่านก่อนอัปโหลดไฟล์ใหม่)

## สิ่งที่พบและแก้ไขแล้วในโค้ดชุดนี้

1. **หน้า Login เดิมไม่ได้ป้องกันอะไรเลย** — โค้ดเช็ก username/password ทำงานอยู่ในเบราว์เซอร์ของผู้ใช้เอง
   ใครก็ตามที่กด "View Page Source" หรือเปิด DevTools จะเห็น `stnkongchang / ytctest2026`
   ได้ทันที และต่อให้ไม่รู้รหัสผ่าน ก็ยังสามารถเรียก Firestore database ตรง ๆ ผ่านค่า
   `firebaseConfig` (ซึ่งก็อยู่ในไฟล์ JS ที่ส่งให้ทุกคนที่เข้าเว็บเหมือนกัน) ได้โดยไม่ต้องผ่านหน้า
   Login เลย เพราะฐานข้อมูลไม่ได้ตั้งกฎ (Security Rules) บังคับให้ต้องพิสูจน์ตัวตนก่อน
   → **แก้แล้ว**: เปลี่ยนไปใช้ Firebase Authentication จริง + ตั้ง Firestore Security Rules
   บังคับให้ต้องล็อกอินก่อนถึงจะอ่าน/เขียนข้อมูลได้ (รายละเอียดขั้นตอนด้านล่าง)

2. **บางจุดเสี่ยงถูกฝังโค้ดอันตรายผ่านข้อมูล (Stored XSS)** — หน้าการ์ดคำร้องและแกลเลอรีรูปภาพ
   เอาข้อมูล เช่น ชื่อเรื่อง, ชื่อผู้ร้อง, ลิงก์รูปภาพ ไปแปะใน HTML ตรง ๆ โดยไม่ได้ป้องกัน ถ้าใครแอบ
   เขียนข้อมูลปลอมเข้าฐานข้อมูลได้ (จากข้อ 1) ก็อาจฝังสคริปต์อันตรายที่ทำงานทันทีที่เจ้าหน้าที่เปิดดูได้
   → **แก้แล้ว**: เพิ่มฟังก์ชัน `escapeHtml()` และ `safeImageSrc()` แปลงข้อมูลก่อนแสดงผลทุกจุดที่เสี่ยง

3. **ค่า `apiKey` ใน firebase-config.js ไม่ใช่ความลับ** — ไม่ต้องกังวลว่ามันถูกมองเห็นได้ เพราะ Firebase
   ออกแบบมาให้ค่านี้อยู่ในโค้ดฝั่งไคลเอนต์ได้ตามปกติอยู่แล้ว **ตัวที่ป้องกันข้อมูลจริง ๆ คือ Security
   Rules ในข้อ 1** ไม่ใช่การซ่อนไฟล์นี้

## สิ่งที่ต้องทำต่อในหน้า Firebase Console (ทำครั้งเดียว)

### ขั้นตอนที่ 1 — เปิดใช้งาน Email/Password Authentication
1. ไปที่ https://console.firebase.google.com/ เลือกโปรเจกต์ `data-kongchang`
2. เมนูซ้าย **Build > Authentication** > กด **Get started**
3. แท็บ **Sign-in method** > เลือก **Email/Password** > เปิดสวิตช์ **Enable** > **Save**

### ขั้นตอนที่ 2 — สร้างบัญชีผู้ใช้งานจริง (แทนบัญชีปลอมเดิม)
1. ยังอยู่หน้า Authentication > แท็บ **Users** > กด **Add user**
2. ช่อง Email ให้ใส่ตามรูปแบบ `ชื่อผู้ใช้เดิม@stnkongchang.local` เช่น
   ```
   stnkongchang@stnkongchang.local
   ```
   (โค้ดฝั่งหน้าเว็บจะแปลง "ชื่อผู้ใช้งาน" ที่พิมพ์ในฟอร์ม Login ให้เป็นอีเมลรูปแบบนี้ให้อัตโนมัติ
   เจ้าหน้าที่จึงยังพิมพ์แค่ username เดิมได้ตามปกติ ไม่ต้องรู้เรื่องอีเมลนี้เลย)
3. ช่อง Password ให้ตั้ง **รหัสผ่านใหม่ที่คาดเดายากกว่าเดิม** (รหัสเดิม `ytctest2026` ถือว่าหลุดไปแล้ว
   เพราะฝังอยู่ในโค้ดที่ส่งให้ทุกคนมานาน ต้องเปลี่ยนเป็นรหัสใหม่เท่านั้น) แนะนำอย่างน้อย 12
   ตัวอักษร ผสมตัวเลข/อักษรพิมพ์ใหญ่-เล็ก
4. กด **Add user**
5. ถ้ามีเจ้าหน้าที่หลายคนใช้งาน แนะนำสร้างบัญชีแยกคนละบัญชี (เช่น `somsak@stnkongchang.local`,
   `malee@stnkongchang.local`) จะได้ตรวจสอบย้อนหลังได้ว่าใครแก้ไขอะไร ปลอดภัยกว่าบัญชีรวมบัญชีเดียว

### ขั้นตอนที่ 3 — ตั้ง Firestore Security Rules
1. เมนูซ้าย **Build > Firestore Database** > แท็บ **Rules**
2. ลบกฎเดิมทั้งหมด แล้ววางเนื้อหาจากไฟล์ `firestore.rules` ที่แนบมาในชุดนี้แทน
3. กด **Publish**

> ถ้าฐานข้อมูลยังอยู่โหมด "Start in test mode" เดิม กฎจะหมดอายุอัตโนมัติใน 30 วันแล้วเว็บทั้งเว็บ
> จะใช้งานไม่ได้ทันที ควรตั้งกฎใหม่ตามข้อ 3 นี้โดยเร็วไม่ว่าจะกังวลเรื่องความปลอดภัยหรือไม่ก็ตาม

### ขั้นตอนที่ 4 — อัปโหลดไฟล์ชุดใหม่ทับของเดิม
แทนที่ไฟล์ทั้ง 4 ไฟล์ (`index.html`, `script.js`, `style.css`, `firebase-config.js`) บนโฮสติ้งที่ใช้อยู่
ด้วยไฟล์จากชุดนี้ แล้วทดสอบล็อกอินด้วยบัญชีที่สร้างในขั้นตอนที่ 2

## ผลลัพธ์หลังทำครบทุกขั้นตอน
- ต่อให้เปิด DevTools หรือรู้ค่า `firebaseConfig` ก็เขียน/อ่านฐานข้อมูลไม่ได้แล้ว ถ้าไม่ได้ล็อกอินจริง
  (เซิร์ฟเวอร์ของ Firebase เป็นคนตรวจสอบ ไม่ใช่โค้ดในเบราว์เซอร์)
- ต่อให้มีข้อมูลแปลกปลอมหลุดเข้าฐานข้อมูลมาได้ ก็จะไม่ถูกรันเป็นสคริปต์ในหน้าเว็บ
- ยังใช้งานแบบเดิมได้ทุกอย่าง (พิมพ์ username/password หน้าตาเดิม, ข้อมูลซิงก์เรียลไทม์เหมือนเดิม)

## แนะนำเพิ่มเติม (ไม่บังคับ แต่ช่วยได้)
- **Firebase App Check**: เพิ่มการยืนยันว่าเป็นเว็บของเราจริง ๆ ที่เรียก Firestore ป้องกันการยิง
  request ปลอมจากภายนอก (ตั้งค่าในเมนู Build > App Check)
- **Firebase Hosting**: ถ้ายังไม่ได้ใช้ Firebase Hosting หรือ HTTPS อยู่ แนะนำย้ายมาใช้ เพื่อให้มี HTTPS
  และตั้งค่า security headers เพิ่มเติมได้ง่าย
- รูปภาพที่แนบตอนนี้เก็บเป็น base64 ฝังอยู่ในเอกสาร Firestore โดยตรง (จำกัดเอกสารละ 1MB) ถ้าจำนวน
  คำร้องและรูปภาพเยอะขึ้นมาก ๆ ในอนาคต แนะนำย้ายไปเก็บใน Firebase Storage แทน จะยืดหยุ่นกว่า
